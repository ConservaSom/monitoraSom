# Golden notes — `run_matching` (ORIGINAL behaviour)

Generated by `R/sandbox/run_matching.R` from `R/original/run_matching.R`
(+ `run_matching_i.R` + `fetch_score_peaks_i.R`). These capture the **faithful
original** batch-wrapper behaviour — bugs included. Runs **single-core on Linux**
(the `sink` path); the Windows PSOCK branch is not reachable here and is
documented from source below.

Reference: `plans/plan-logs/plan-log-2026-06-04-001.md` + `-2026-06-05-001.md` +
`-2026-06-07-001.md` (Stage 4 gate). DEBT log: `RMB`
(`DEBT_INVENTORY_LOG-run_matching.md`).

The Stage-6 refactor **redesigns this wrapper** (mirai + soundscape-group
traversal + spectrogram cache + DuckDB/Parquet persistence; CSV/RDS deprecated),
so most of these goldens are captured to **document the legacy contract** and the
bugs being dissolved — they are asserted as **derived** expectations (and several
as *"the refactor no longer does this"*), not verbatim equality.

## Intentional divergences (refactor CHANGES these — assert as derived)

The Stage 4 gate (`plan-log-2026-06-07-001.md` §2.2) **deprecates CSV/RDS** and
migrates to DuckDB/Parquet, so these legacy behaviours are **not** reproduced —
the refactor either replaces them or fixes them:

- **RMB-02 — parallelism split.** The Windows PSOCK + `clusterEvalQ` library
  preload (source lines 141–162, 253–268) vs the Unix fork/`sink` path are not
  exercised here (single-core Linux). The refactor unifies on **`mirai`**, so
  these branches vanish. *No golden; documented from source.*
- **RMB-03 / RMB-06 — CSV write strategy.** `G2` shows the legacy `writeLines`
  header + per-row `sink`/`write.table` append. The refactor writes detections to
  a **DuckDB table** (transactional upsert); the CSV is produced only by a
  back-compat converter. → assert the **DuckDB** output; `G2` documents the old
  byte layout (its `.md5`/content embed **absolute paths**, so byte-identity is
  machine-relative — do not assert across machines).
- **RMB-04 — append dedup keyed only on `soundscape_file`.** `G3` demonstrates the
  bug: after seeding the CSV with t092 → ss092000, an `append` run of a
  **different template** (t075) against the **same** soundscape (ss092000) returns
  **`NULL`** with *"All matches have already been processed"* — the new match is
  silently dropped. The refactor's DuckDB **upsert keys on
  `(soundscape_path, template_id, peak_index)`**, so a different template is kept.
  → assert the refactored append **keeps** the cross-template match (opposite of
  this golden).
- **RMB-05 — hardcoded 21-col CSV header.** `G2`'s header is the hand-maintained
  vector (source lines 197–204). The refactor derives the schema from
  `_schema_detections.R` (single source of truth). → no hand-kept header.
- **RMB-08 — `do.call(rbind)` vs `list_rbind`.** `G1` uses `do.call(rbind)`
  (brittle on zero-row frames); `G4` already uses `list_rbind`. The refactor
  standardizes on `list_rbind`/`bind_rows` for both. (Both pairs yield detections
  here, so `G1` binds cleanly — the divergence is robustness, not values.)
- **Scores persistence (RMB / gate §2.2).** `G5` is RDS. The refactor persists raw
  scores as a **DuckDB array column AND/or Parquet** (transient rejected). → assert
  DuckDB/Parquet round-trip, not the `.rds`.

## Asserted directly in testthat (no golden needed)

- **RMB-01 / RMB-10** `ncores` validation: only an upper bound today
  (`> detectCores()`), `detectCores()` called twice, `NA` unguarded. Refactor:
  positive-integer + `NA`-guard, cached once.
- **RMB-07** scores-branch path validation runs **after** the whole batch (late
  failure); refactor validates `output_db` up front for both branches.
- **RMB-12** empty `df_grid` → `split(df_grid, seq(0))` misbehaves; refactor
  short-circuits with a friendly message (`seq_len`).
- **RMB-13** `score_method` must accept **`"fft"`** (today only `cor`/`dtw`).
